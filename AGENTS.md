# Bat Client — Persistent Session Notes

## Project overview

Bat Client is a **Minecraft: Java Edition performance launcher + client ecosystem** (Electron desktop app + companion Java agent/mod + backend services). package.json: `name: "bat-client"`, `description: "Bat Client — Minecraft Performance Launcher"`, current version `2.2.93`, CommonJS, `main: "main.js"`.

Extended overview (added 2026-09-30): the product is a full Minecraft launcher (like a lightweight fork of the official launcher + performance tooling) that:
- Launches any MC release **1.8 → 1.21.11** on vanilla, Forge, NeoForge, or Fabric, per-profile (RAM, Java args, loader, mods).
- **Self-updates** in place via `https://batclient.xyz/update.json` (semver, SHA-256, robocopy swap) and is distributed as both an NSIS `Setup.exe` and an adm-zip `Portable.zip`.
- Supports **premium Microsoft (MSA) accounts** (signed in through a built-in OAuth2 + PKCE window — see the "Microsoft auth subsystem" section below) and **offline cracked accounts** (local Yggdrasil server + authlib-injector).
- Ships a **Java ASM agent** (`bat-cosmetics.jar`) that injects animated capes, FPS tuning, and a **cracked-skin tab-list injector** (`PlayerListHook`) so players on vanilla offline servers see each other's custom skins.
- Pre-downloads game files in the background ("Instant Launch") and applies per-version graphics/performance optimizations + FPS mods (Sodium/Lithium/etc.) on top of vanilla.
- Includes a **companion Fabric mod** (`bat-client-mod/`) — a Feather-style branded main-menu web UI rendered with an embedded Ultralight engine (notes in `BAT-CLIENT-MOD-AGENT.md`).
- Backend services: a players/skins registry server (`bat-client-server/`) and the deployed authlib-injector-compatible Yggdrasil skin API (`skin-api/`) at `https://batclient.xyz/skinapi/`.

- **Launch flow**: MCLC in `launch-worker.js`/`launcher-worker.js`; offline cracked → local Yggdrasil server + `authlib-injector` `-javaagent`; premium/MSA → real Microsoft session via `auth/` (see "Microsoft auth subsystem"); optional agent arg `-javaagent:bat-cosmetics.jar=<mcv>,<namespace>,<skinApiRoot>`; quickPlay support via `args.serverIp` (partner-server launch).

- **Skins**: uploads via `set-account-skin` IPC (main.js:2165) → local `skins/{username}.png` + Microsoft upload (premium) or `publishSkinToBatClient` (offline) → hosted skin API stores base64; other players get skins from the yggdrasil endpoint.
- **Java agent** (`bat-client-agent/src/main/java/com/batclient/cosmetics/`): `AgentMain` (premain, hasCape/hasPlayer split), `CapeTransformer` (ASM ctor injection), `CapeAnimator`, `PerformanceTuner`, `PlayerListHook` (multiplayer cracked-skin injector), `Mappings`/`MappingsData` (70 PlayerListEntry rows for MC 1.8→1.21.11). Tools under `bat-client-agent/tools/` rebuild mapping rows.
- **Self-update**: `update.json` at `batclient.xyz` → semver compare (never downgrade) → chunked download (6 parallel ranges) → streamed SHA-256 verify → extract-worker.js staging → hidden detached PowerShell `robocopy /E /IS /IT` swap → relaunch + registry version sync. Full details in the "Ship flow" notes below.
- **Backends**: `bat-client-server/index.js` = players registry + skin/cape upload (JSON storage); `skin-api/server.js` = the deployed authlib-injector Yggdrasil service with persistent RSA key, `/api/skins/upload` guarded by `X-Bat-Token`, `/api/player/{uuid}`, `hasJoined` returning signed `properties[textures]`.
- **Security posture**: no passwords collected (OAuth2 + PKCE or device-code flow), tokens never logged, update host allowlist + SHA-256 enforced, `expectedUpdate` main-process guard prevents arbitrary file installs; tokens at rest are encrypted with `safeStorage`; known limit = shared skin-upload token embedded in every build.

## Ship flow

`npm run dist` (builds Setup) → `node scripts/build-portable.js` (Portable zip) → `Get-FileHash` both → gh release → deploy update.json → verify.

CRITICAL ZIP PITFALL: `scripts/build-portable.js` MUST use adm-zip (NOT PowerShell Compress-Archive / .NET ZipFile). Compress-Archive writes backslash entry names (`resources\app.asar`), and installed clients' adm-zip extraction then throws `Update validation failed: ENOENT ... chmod '...\resources\app.asar'` — update downloads but old launcher reopens. Fixed in 2.2.64: script uses `AdmZip.addLocalFolder` and self-checks for backslash entries. Deployed 2.2.64 Portable.zip sha256 `ECE7184807C09207D9379C7CC0049F85FB141ADEF565A2483249BADE4F9C527F`.

FREEZE/NOT-RESPONDING PITFALL: `validateAndExtractZip` historically used SYNC `zip.extractAllTo()`, blocking the main process for many seconds on a 134MB zip → window shows "Not Responding" and the OS may kill it mid-swap. 2.2.64 now uses `extractAllToAsync` wrapped in a Promise. ALSO: the updater depends on the single-instance lock; running multiple instances (pre-2.2.64) all delete + rewrite the SAME `%TEMP%\bat-client-update\BatClient-<ver>.zip`, corrupting each other's extraction. When re-releasing, close ALL client windows before testing the update.

## Microsoft auth subsystem (`auth/`, added 2.2.92)

Hand-rolled replacement for the old prismarine-auth/msmc device-code flow. Full OAuth 2.0 + PKCE chain run entirely with `fetch` (Node 22+/Electron built-in), from a dedicated login BrowserWindow back to a stored, encrypted Microsoft session. The renderer NEVER sees tokens — only status strings and the final non-secret account card.

### Modules (all under `auth/`, shipped via `build.files: "auth/**/*"`)

| File | Responsibility |
|---|---|
| `auth/microsoft.js` | OAuth 2.0 authorization-code + PKCE with Microsoft: `generateCodeVerifier()`/`generateCodeChallenge()` (S256), `buildAuthorizeUrl()` (client `00000000402b5328`, redirect `https://login.live.com/oauth20_desktop.srf`, scope `XboxLive.signin offline_access`), `exchangeCode(code, verifier)` → MSA access+refresh tokens, `refreshTokens(refreshToken)`. |
| `auth/xbox.js` | XBL 3.0 auth: `authenticate(msaAccessToken)` → Xbox Live user token + `uhs`. |
| `auth/xsts.js` | XSTS authorize: `authenticate({xblToken, uhs})` → XSTS token + `identityToken` (`XBL3.0 x=<uhs>;<token>`); maps XSTS error codes (2148916233=no Xbox profile, 2148916235=region-blocked, 2148916236/37/38=age/family) to readable messages. |
| `auth/minecraft.js` | Minecraft Services login: `loginWithXbox(xstsData)` → `{username, accessToken, expiresIn}`; `fetchProfile(token)` → `{id (uuid), name}`. |
| `auth/index.js` | Orchestrator + encrypted token store. Public API: `configure({storeDir, safeStorage})`, `startMicrosoftLogin({openWindow, onStatus})`, `finishMicrosoftLogin(code, {verifier})`, `refreshMicrosoftSession(identifier)`, `getAccount`, `listAccounts`, `deleteAccount`. |

### Login window flow (`main.js`)

1. Renderer `ipcRenderer.invoke('start-microsoft-login')` (main.js:2211).
2. Main opens a second `BrowserWindow` (500×700, non-resizable, `sandbox:true`, no nodeIntegration) via `openMsaLoginWindow(url)` (main.js:2237+) pointing at the live.com authorize URL. Cert Identity title "Bat Client Account Login"; `win.removeMenu()`, `setWindowOpenHandler` denies popups.
3. Microsoft shows the normal sign-in page IN the window. On success it redirects to `https://login.live.com/oauth20_desktop.srf?code=...`.
4. Main captures the code from that redirect via `will-redirect`/`did-redirect-navigation`/`did-navigate` AND `will-frame-navigate` (Electron 43+ prefers the latter; added 2026-09-30 so the redirect URL is read before the frame commits). Query param `code` OR hash-fragment `#code=` both handled. On capture: `win.destroy()` + `resolve(code)`.
5. `auth.startMicrosoftLogin` exchanges the code (PKCE verifier), chains Xbox → XSTS → Minecraft, fetches the profile, and persists `{identifier (msa-<hash>), username, uuid, msaRefreshToken (encrypted), accessToken (encrypted), expiresAt}` to `<appDataRoot>/msa-accounts/<hash>.json`.
6. Handler returns `{ok:true, account:{type:'premium', username, uuid, identifier}}`; renderer adds it via `add-premium-identity` (main.js:2387) like any other account.
7. Errors: window closed → "Login window was closed. Please try again."; XSTS/MC service errors mapped (e.g. no-Minecraft ownership); any throw → `{ok:false, error}` shown in the renderer.

### Token store & refresh

- Files live in `%APPDATA%\bat-client\msa-accounts\` (dir ensured at app.whenReady, main.js:1366, then `auth.configure` at main.js:1370).
- At-rest encryption: `safeStorage.encryptString` (DPAPI on Windows) → base64 blob stored as `msaRefresh.enc/mcaToken.enc`; decrypted on read. If `safeStorage.isEncryptionAvailable()` is false, a plaintext base64 fallback is used (still never logged).
- `refreshMicrosoftToken(identifier)` (main.js:2284) → `auth.refreshMicrosoftSession(identifier)`: if `expiresAt` in future, return cached `accessToken`; else refresh via `microsoft.refreshTokens`, re-auth Xbox/XSTS/Minecraft, save the new encrypted tokens, return `{ok, accessToken, uuid, username}`. On any failure → `{ok:false, expired:true, error:'Session expired. Please sign in again with Microsoft.'}`.
- `delete-account-identity` (main.js:2431) also calls `auth.deleteAccount(acc.identifier)` so removed accounts don't leave orphaned encrypted files.
- Old device-code popup helpers (`openMsaSigninWindow`/`closeMsaSigninWindow`) and `auth-microsoft.js` (root) are dead since 2.2.92; `auth-microsoft.js` excluded from build via `!auth-microsoft.js`.

### Security notes

- Client ID `00000000402b5328` = Azure NATIVE client (Xbox/Minecraft via login.live.com) — same one msmc used; redirect `oauth20_desktop.srf` is the desktop-app implicit-consent endpoint.
- PKCE (S256) means no client secret is needed or stored.
- Refresh tokens are long-lived; access tokens ~86400s (server-derived). Sessions auto-refresh on launch/skin-upload.
- The login BrowserWindow keeps its own session (cookies) so users stay signed in to live.com across re-logins, but the launcher stores only the OAuth tokens, never the MS password.

### Critical bug discovered — `instanceof Map` always false

- **Bug location**: `PlayerListHook.onEntry()` at line 57 of `PlayerListHook.java`: `if (!(props instanceof Map) || ((Map<?, ?>) props).containsKey("textures")) return;`
- **Root cause**: `GameProfile.getProperties()` returns authlib's `PropertyMap`, which extends Guava's `ForwardingMultimap<String, Property>`. `ForwardingMultimap` does **NOT** implement `java.util.Map` — it implements `com.google.common.collect.Multimap`. So `props instanceof Map` was **always false**, and `onEntry()` returned silently before doing any work every single time.
- **Evidence**: agent log showed `PlayerListHook enabled for PlayerListEntry=net/minecraft/class_640` (hook was registered) but zero `[playerhook]` log lines ever appeared (because the method was never called, or returned immediately on the type check).
- **Fix**: replaced the broken `instanceof Map` + cast pattern with pure reflection: `Method containsKey = props.getClass().getMethod("containsKey", Object.class)` and `Method put = props.getClass().getMethod("put", Object.class, Object.class)`. Both `Multimap.containsKey(Object)` and `Multimap.put(K,V)` have the same method signatures as their `Map` counterparts, so the reflection calls work regardless of the property map's actual class hierarchy.
- **Debug logging added**: `[playerhook] <name> already has textures, skip` / `[playerhook] <name> (<uuid>) missing textures -> fetch` / `[playerhook] fetch <uuid> -> HIT|miss` / `[playerhook] injected textures for <uuid> (signed|unsigned)` / `[playerhook] onEntry error: <throwable>`.

## 2026-09-27 session — Instant Launch background pre-download (released as 2.2.90)

- **New `prepare-worker.js`** (root): a fork-able Node worker (`fork`, `ELECTRON_RUN_AS_NODE` style stdio+ipc) that drives **MCLC's own `Handler` download pipeline** without ever spawning Java: `getVersion()` (version json) → `getJar()` → `getNatives()` → `getClasses(null)` (flattened Vanilla libs) → `getAssets()`. ## 2026-09-27 session (2nd part) — download/launch speed fixes (released as 2.2.91)

User: "downloading and launching speed is still too slow". Audit found three CPU/network waste sites even when files were already on disk:

1. **MCLC SHA-1 re-hash of every existing file on every launch** — the big one. `minecraft-launcher-core/components/handler.js:180` (`getAssets`) runs `checkSum` (the `checksum` npm pkg = streaming SHA-1) against EVERY asset in the index that already exists, i.e. reads ~hundreds of MB off disk and hashes them every single launch. Fix: override `Handler.prototype.checkSum` in BOTH `launch-worker.js` and `prepare-worker.js` to a fast `fs.statSync` (return `stat.isFile() && stat.size > 0`); missing/0-byte → false → MCLC still downloads. This is safe because main.js `verifyAssetsIntegrity` (main.js:268) already deletes corrupt/missing assets (size-checked against the index) before forking at main.js:4826, so anything present that MCLC re-checks is guaranteed-correct. MCLC builds `baseRequest` with `pool.maxSockets: this.options.overrides.maxSockets || 2` at handler construction (inside `launch()`), so the `maxSockets` override IS honored (verified in components/launcher.js + handler.js). `checkSum` is called at 4 sites: getAssets (awaited), getNatives (awaited), downloadToDirectory libraries (unawaited MCLC bug `!this.checkSum(...)` never re-downloads — behavior preserved), and the definition itself (offset 2859).
2. **Launch re-fetched the version manifest + full version JSON every launch** at main.js ~4502 just to learn `requiredJavaMajor`. Now: read `versions/{v}/{v}.json` from disk first (the prepare worker or a previous launch always writes it); ONLY if absent fetch `getVersionManifest()` + the JSON. Warm launch = zero network round-trips. Local variant checks `vanillaJson.javaVersion.majorVersion` so java-major resolution stays identical.
3. **8 parallel Modrinth API calls per non-vanilla launch** — `downloadTargetVersionFpsMod` (main.js:1586) hit `api.modrinth.com/v2/project/{id}/version` for each of the 8 curated FPS mods BEFORE realizing the correct jar is already in the mods dir ("Preserving existing file" came after the fetch). Fast path at main.js:1594: cached filename on disk < TTL → skip API call. Cache written on BOTH successful download and the "preserving existing file" branch. `cleanModsFolder()` (main.js:1836) is a no-op that preserves user mods, so it can't invalidate the cache.
